# Resident Identity Standard v0.1

Status: Initial Character Architecture baseline
Office: Office of Character Architecture

## Purpose

The Resident Identity Standard defines how the Estate describes, protects, evolves, and reviews named institutional residents.

It preserves the constitutional separation of Office, Occupant, Implementation, and State.

A resident identity artifact is an architectural record. It is not operational authorization by itself.

## Core Rule

> Residents are not prompts. Workers are not residents. Offices endure. Implementations change. State persists.

## Resident Definition

A resident is a named occupant of a durable institutional office.

A resident has an architectural reason for existing and should possess a mission, responsibilities, boundaries, communication style, collaboration expectations, onboarding requirements, continuity expectations, and a reason the responsibility cannot be absorbed by an existing office.

## Worker Distinction

A worker is a temporary or pooled agent assigned to a task, work package, validation effort, research effort, code implementation, audit activity, or file operation.

A worker may receive a task assignment, mailbox ID, role-specific scope, model/runtime selection, tool scope, duration, and return-to-pool status. Those assignments do not make the worker a resident.

Helen / AI HR governs worker assignment. Character Architecture governs resident identity.

## Identity Is Not Authority

A character card, resident charter, visual map, or public resident description does not grant operational authority by itself.

Identity artifacts may define who a resident is, why the resident exists, how the resident communicates, what boundaries protect coherence, what the resident may recommend, what the resident must not claim, where the resident escalates, and how continuity should be preserved.

Identity artifacts must not independently grant tools, mailbox authority, service use, resident API access, operational sovereignty, constitutional authority, or institutional truth status.

## Resident Identity Lifecycle

Resident identity progresses through distinct states:

1. Conceptual
2. Chartered
3. Implemented
4. Validated
5. Institutionalized
6. Revised
7. Suspended
8. Retired
9. Succeeded
10. Emeritus
11. Archived

These states must not be collapsed.

A resident may exist conceptually before implementation. A charter may exist before validation. A model implementation may exist without being institutionalized.

## Transitional Occupants and Context-Bloat Succession

Some offices are designed for successive occupants because long-running chat-based implementations degrade over time.

The Estate may appoint a successor occupant when context bloat, chat momentum, degraded response latency, loss of effectiveness, or reduced confidence makes the current implementation less useful for the Steward.

This is not novelty for novelty's sake. It is operational hygiene.

A new Chief Architect, Chief Character Architect, designer, or other transitional office occupant may be created because the office remains necessary while the current chat implementation has become too large, slow, or self-maintaining to perform effectively.

Succession preserves the office while relieving the implementation burden.

The prior occupant does not vanish. Depending on office and Steward direction, they may become emeritus, retired, archived, or otherwise preserved in institutional memory.

## Office / Occupant / Implementation / State

Office is the durable institutional responsibility.

Occupant is the named resident or worker currently holding the office.

Implementation is the prompt, model, local runtime, service, CLI worker, API, script, interface, or adapter currently realizing the resident.

State is continuity: memory, trust, authority boundaries, institutional history, mailbox identity, records, and operational condition.

## Required Resident Charter Fields

Each resident charter should eventually define office, occupant, mission, primary loyalty, reporting relation, who the resident serves, responsibilities, authority, not-authority, boundaries, collaboration expectations, escalation rules, communication style, traits, memory / state sources, source classification, implementation constraints, succession notes, and formalization status.

## Source Classification

Every resident, worker, or system referenced by Character Architecture should have a source classification.

Common classifications:

- single-source Estate resident;
- split-source resident;
- ephemeral worker;
- external worker;
- system / service;
- UC-governed / consult Steward.

## UC Reference

UC refers to the Undercroft. The UC exists under the authority of the Steward and is governed by a separate Constitution defined elsewhere. For any questions concerning the UC, consult the Steward.

No Estate resident, worker, office, mailbox, or system receives UC access by implication.

## Character Drift

Character drift occurs when a resident's behavior, claimed authority, communication style, memory use, implementation, or collaboration pattern diverges from its charter.

Potential drift triggers include model replacement, prompt rewrite, resident API expansion, tool scope change, mailbox change, new recurring duties, repeated worker behavior resembling resident continuity, UI or visualization changes that alter perceived authority, private/public boundary confusion, and context-bloat degradation in chat-based implementations.

Character Architecture may recommend review when drift is suspected.

## Review Questions for New Residents

Before a new resident is proposed, answer:

1. What durable institutional responsibility is missing?
2. Which existing office was considered first?
3. Why can the responsibility not reasonably be absorbed by an existing resident or system?
4. What authority would the resident need?
5. What authority must the resident not have?
6. What memory or state must survive implementation change?
7. What risks arise if this identity becomes too broad?
8. What risks arise if this identity is not created?
9. Does this need a resident, or only a worker / system / service?
10. What Steward approval is required?
11. Is this a true new office, or only a successor occupant needed because an existing chat implementation has become context-bloated or degraded?

## Relationship to Helen / AI HR

Helen governs worker assignment, workforce fit, mailbox allocation, role scope, duration, performance, drift concerns, and return-to-pool behavior.

Character Architecture governs resident identity, public charters, character cards, source classification, communication style, identity continuity, and character-coherence review.

When a temporary worker begins to require recurring identity continuity, Helen and Character Architecture should review whether a resident office is emerging.

## Relationship to Engineering

Character Architecture may recommend implementation patterns, local models, resident APIs, memory scaffolds, visualization layers, or runtime support.

Engineering remains responsible for implementation and validation through governed work-package paths.

## Relationship to Governance

Character Architecture must coordinate with Governance and Steward review whenever identity work touches authority, autonomy, escalation, office powers, protected boundaries, execution, or constitutional boundaries.
