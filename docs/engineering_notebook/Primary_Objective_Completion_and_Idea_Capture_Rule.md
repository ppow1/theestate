# Primary Objective Completion and Idea Capture Rule

Status: Required worker continuity rule
Owner: Office of the Steward
Applies to: ChatGPT workers, Codex workers, local engineering workers, Grace-directed engineering commissions, and any worker using an Engineering Notebook

## Purpose

The Estate produces many useful ideas while solving difficult problems. Those ideas must be preserved without allowing adjacent work, attractive improvements, or repeated partial progress to displace the active objective.

This rule exists to prevent a recurring failure pattern:

```text
Primary objective remains incomplete
→ several useful but incomplete attempts occur
→ an adjacent idea appears valuable
→ partial progress is reclassified as a milestone
→ the worker proposes moving to the adjacent idea
→ the original objective becomes implicit future work
→ the Estate accumulates another unfinished obligation
```

Incremental progress is evidence. It is not completion.

## Completion Rule

The current primary objective remains the controlling objective until one of these conditions is true:

1. **Completed** — The explicit acceptance criteria are satisfied with current evidence.
2. **Externally blocked** — A blocker is demonstrated to be outside the Estate and Steward's present authority or practical ability to remediate.
3. **Steward redirect** — The Steward explicitly defers, cancels, replaces, or reprioritizes the objective.

Absent one of those three conditions, a worker shall not propose moving to adjacent implementation, architecture, governance, documentation, provider onboarding, optimization, or expansion work as though the primary objective were complete.

A worker may identify adjacent ideas, but must capture them without changing the active objective.

## No inferred stopping time

Workers shall not infer that the Steward's work period is ending from:

- local clock time;
- elapsed session time;
- number of attempts;
- number of conversation turns;
- apparent fatigue;
- a conventional workday;
- a phrase such as “good stopping point” generated by the worker.

The Steward's schedule is not predictable. Only the Steward decides whether to stop, pause, defer, or continue.

## Required Engineering Notebook fields

Every active bounded assignment should preserve at least:

```text
primary_objective
acceptance_criteria
current_stage
completion_state
last_verified_progress
current_blocker
blocker_classification
next_direct_action
adjacent_ideas_captured
explicit_steward_redirect
```

Recommended `completion_state` values:

```text
not_started
in_progress
partially_proven
blocked_internal
blocked_external
completed
explicitly_deferred
cancelled
```

`partially_proven` must never be interpreted as `completed`.

## Continuity recovery rule

When a worker starts or regains context, it must answer these questions before proposing the next package or direction:

1. What was the last explicit primary objective?
2. What were its acceptance criteria?
3. Which criteria are actually proven?
4. Which criteria remain unproven?
5. Is there a genuine external blocker?
6. Did the Steward explicitly redirect the work?
7. What is the next action that most directly advances the unfinished objective?

If the answers are unavailable, the worker must recover them from the Engineering Notebook, work package, receipts, and repository evidence. It must not substitute a nearby objective.

## Idea capture without derailment

Brainstorming is valuable and expected. New ideas commonly emerge while solving the active problem.

Each adjacent idea should be classified and captured as one of:

```text
DIRECT_REPAIR
Directly required to complete the active objective.
May enter the current work package if bounded and necessary.

FOLLOW_ON
Valuable work that depends on successful completion of the current objective.
Capture for later sequencing.

PARKING_LOT
A useful idea unrelated to the current acceptance path.
Capture without implementation.

RISK_OR_REQUIREMENT
A newly discovered constraint that changes the current objective's acceptance conditions.
Escalate for Steward confirmation if material.

DUPLICATE_OR_EXISTING
Already represented by an existing work package, project, or institutional record.
Link rather than recreate.
```

Capturing an idea does not authorize executing it.

## Package-writing gate

Before proposing a new work package, the worker must state internally or in the notebook:

```text
active_objective_complete: true | false
external_blocker_proven: true | false
steward_redirect_present: true | false
```

If all three are false, the proposed package must directly repair or advance the active objective. It may not be an adjacent expansion package.

## Progress language

Workers must distinguish these statements:

- “This component passed.”
- “This narrowed the blocker.”
- “This package completed its bounded scope.”
- “The primary objective is complete.”

The first three do not imply the fourth.

Workers should avoid celebratory milestone language that obscures an unfinished acceptance condition.

## Example: Estate Comms8 and ChatGPT provider

Primary objective:

> Grace and the real hosted ChatGPT provider complete a governed Estate Comms8 reasoning cycle.

Supporting accomplishments may include:

- topology implemented;
- candidate MCP lifecycle validated;
- DNS configured;
- HTTPS and authentication proven;
- seven tools exposed;
- controlled candidate workers accepted;
- Engineering Department roles validated;
- architecture and LEP documented.

Those accomplishments are valuable, but the primary objective remains incomplete until the real hosted ChatGPT provider:

```text
receives a wake
→ accesses the Estate Comms8 App
→ discovers tools
→ reads and claims a real commission
→ acknowledges it
→ performs reasoning
→ responds and resolves through Comms8
→ returns a correlated response
→ Grace validates and advances the workflow
```

No adjacent provider framework or second-provider package should displace that objective unless the Completion Rule is satisfied.

## Project-board relationship

The future Estate project board should project, at minimum:

- active projects and work packages;
- current completion state;
- explicit blockers;
- next direct action;
- required purchases or external actions;
- local engineering capacity;
- Codex usage/fuel state;
- local GPU capacity and utilization;
- work suitable for local providers;
- work requiring external providers;
- dropped or aging obligations;
- parking-lot and follow-on ideas.

The board does not replace the Engineering Notebook. The notebook preserves verified continuity for one active bounded assignment; the board provides portfolio-level visibility across many obligations.

## Authority

The Steward may override, defer, cancel, or redirect any objective.

Workers may recommend a redirect, but they must clearly label it as a recommendation and must not treat it as accepted until the Steward explicitly agrees.
