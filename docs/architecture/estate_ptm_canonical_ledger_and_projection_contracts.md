## Authority and boundaries

This artifact freezes the canonical PTM ledger and projection contracts for implementation planning. It is source-backed by the accepted PTM baseline, the PTM parallel execution plan, the dependency manifests, and the Gate A read-only adapter contract.

This artifact does not authorize production PTM code, does not mutate authoritative source records, and does not create a second dispatch queue, second registry, second scheduler, validation authority, or governance authority. Existing work-package files, Parking Lot entries, dispatch evidence, validation reports, resident/operations records, and acceptance records remain authoritative in place.

## CORE-PTM-002A append-only event schema and hash chain

### Canonical event envelope

Every future PTM event must use the same append-only envelope before any domain-specific payload fields are interpreted:

```yaml
ptm_event:
  event_id: string
  event_type: string
  event_version: integer
  aggregate_type: portfolio | project | task | intake | file_import | schedule | finance | utilization | kpi | dispatch | migration | rollout | validation
  aggregate_id: string
  stream_id: string
  sequence_number: integer
  occurred_at: string
  recorded_at: string
  actor_ref: string
  authority_refs: [string]
  source_refs:
    - source_path: string
      source_sha256: string
      adapter_name: string
      adapter_version: string
  causation_id: string | null
  correlation_id: string | null
  command_id: string | null
  idempotency_key: string
  payload_schema: string
  payload: object
  previous_event_hash: string | null
  event_hash: string
  hash_algorithm: sha256
```

### Event-type namespace

Event types must use lower-case dotted names with an explicit domain prefix, for example `task.created`, `task.status_changed`, `schedule.readiness_changed`, `finance.budget_adjusted`, `dispatch.evidence_linked`, and `validation.result_recorded`. Downstream packages may add payload schemas under those namespaces but must not change the envelope fields without a stop/replan note.

### Immutability rules

1. Events are append-only: no update, delete, rewrite, or in-place correction is permitted.
2. Corrections are represented by later compensating events with `causation_id` pointing to the event being corrected.
3. Every projected field must trace to one or more `source_refs` and one or more event IDs.
4. Adapter uncertainty must be preserved as payload metadata or projection warnings rather than guessed away.
5. Events may reference source records but may not replace the authority of those records.

### Hash-chain expectations

- `event_hash` is the SHA-256 digest of the canonical serialized event with `event_hash` omitted and keys ordered deterministically.
- `previous_event_hash` links to the previous event in the same `stream_id`; the first event in a stream uses `null`.
- `sequence_number` is strictly increasing per `stream_id` and must match hash-chain order.
- A replay validator must reject missing sequence numbers, duplicate event IDs, duplicate idempotency keys in the same command scope, mismatched previous hashes, and non-deterministic canonical serialization.

### Fixture plan

Future validation fixtures should include:

- a valid single-stream task lifecycle;
- a multi-stream correlation across intake, task, schedule, and dispatch evidence;
- a compensating correction event;
- a broken previous-hash fixture;
- a duplicate idempotency-key fixture;
- an adapter-warning fixture that remains visible in projections.

## CORE-PTM-002B PTM ID minting and command contracts

Detailed CORE-PTM-002B implementation-preparation requirements are frozen in `docs/architecture/estate_ptm_id_minting_command_contract.md`. The summary below is intentionally subordinate to that artifact and must not be used to create a second ID authority, command bus, queue, registry, scheduler, or governance path.

### ID formats

PTM IDs are minted by a single canonical PTM ID service interface and must not be independently generated by downstream features.

| Entity | Format | Notes |
| --- | --- | --- |
| Event | `evt_<ulid>` | Globally unique immutable ledger event ID. |
| Command | `cmd_<ulid>` | One command request envelope. |
| Portfolio | `pf_<slug>_<ulid>` | Stable portfolio aggregate. |
| Project | `prj_<slug>_<ulid>` | Stable project aggregate. |
| Task | `tsk_<slug>_<ulid>` | Stable task aggregate. |
| Intake | `int_<slug>_<ulid>` | Governed intake candidate or accepted intake record. |
| File import | `fil_<slug>_<ulid>` | Import session or source file mapping. |
| Schedule item | `sch_<slug>_<ulid>` | Schedule projection aggregate. |
| Financial item | `fin_<slug>_<ulid>` | Budget, cost, approval, or reconciliation aggregate. |
| KPI item | `kpi_<slug>_<ulid>` | KPI definition, measure, or dashboard aggregate. |
| Dispatch evidence | `dsp_<slug>_<ulid>` | Reference to dispatch evidence, not a queue row. |

`<slug>` is a short normalized human hint; `<ulid>` supplies uniqueness and chronological sort. IDs are never reused after archive, rejection, merge, or correction.

### Command envelope

```yaml
ptm_command:
  command_id: string
  command_type: string
  command_version: integer
  requested_at: string
  requested_by: string
  authority_refs: [string]
  target_aggregate_type: string
  target_aggregate_id: string | null
  idempotency_key: string
  expected_stream_version: integer | null
  source_refs: [object]
  payload_schema: string
  payload: object
  dry_run: boolean
```

### Command handling rules

1. Commands validate authority, source references, idempotency, and expected stream version before emitting events.
2. Commands emit zero events on validation failure and return structured rejection reasons.
3. Dry-run commands produce validation reports only; they do not mint persistent events.
4. CLI, library, UI, and Resident command surfaces must call the same command contract.
5. Commands must not bypass established Steward, Chief Architect, Helen, Grace, Traffic Controller, dispatch, validation, or acceptance boundaries.

## CORE-PTM-003A project, task, portfolio, status, and audit projection contracts

Detailed CORE-PTM-003A implementation-preparation requirements are frozen in `docs/architecture/estate_ptm_project_task_portfolio_projection_contracts.md`. The summary below is intentionally subordinate to that artifact and must not be used to create a second task registry, portfolio registry, dispatch queue, scheduler, or governance path.

### Shared projection envelope

```yaml
ptm_projection_record:
  projection_name: string
  projection_version: string
  record_id: string
  aggregate_type: portfolio | project | task | status | audit
  aggregate_id: string
  source_event_ids: [string]
  source_refs: [object]
  computed_at: string
  high_watermark_event_id: string
  high_watermark_recorded_at: string
  stale: boolean
  warnings: [string]
```

Projection records are deterministic replay outputs. They are not authoritative source records and must be rebuildable from canonical events plus read-only adapter source references.

### Portfolio projection

Minimum fields: `portfolio_id`, `title`, `summary`, `status`, `owner_refs`, `authority_refs`, `project_ids`, `task_ids`, `task_count_by_status`, `blocked_task_count`, `active_package_count`, `completion_receipt_refs`, `risk_warnings`, `latest_event_id`, and the shared projection envelope.

### Project projection

Minimum fields: `project_id`, `portfolio_id`, `title`, `summary`, `status`, `owner_refs`, `authority_refs`, `source_package_refs`, `dependency_refs`, `milestone_refs`, `task_ids`, `schedule_refs`, `financial_refs`, `kpi_refs`, `dispatch_refs`, `validation_refs`, and `audit_summary`.

### Task projection

Minimum fields: `task_id`, `project_id`, `portfolio_id`, `title`, `description`, `status`, `readiness_state`, `owner_or_lane_ref`, `authority_refs`, `dependency_refs`, `source_refs`, `schedule_refs`, `financial_refs`, `dispatch_refs`, `validation_refs`, `completion_receipt_refs`, `latest_event_id`, and `warnings`.

### Status and audit rules

- Status values are normalized as `candidate`, `pending`, `ready`, `claimed`, `in_progress`, `blocked`, `in_review`, `completed`, `accepted`, `rejected`, `archived`, or `superseded`.
- Path-derived status and body-declared status must both be preserved when they disagree.
- Audit projections must expose event IDs, source paths, source hashes, actor refs, command IDs, correction chains, source conflicts, event hashes, and previous event hashes.
- Projection builders must not infer authority, ownership, approval, dispatch state, validation acceptance, budget authorization, or schedule readiness when the supporting event or source reference is absent.

## CORE-PTM-003B schedule, financial, utilization, KPI, and timeline projection contracts

### Schedule projection

Minimum fields: `schedule_item_id`, `task_id`, `dependency_ids`, `readiness_gate`, `critical_path_flag`, `blocked_reason`, `active_estimate_minutes`, `validation_estimate_minutes`, `rework_allowance_minutes`, `queue_wait_minutes`, `review_wait_minutes`, `expected_wall_clock_minutes`, and `warnings`.

### Financial projection

Minimum fields: `financial_item_id`, `project_id`, `task_id`, `budget_ref`, `cost_ref`, `approval_refs`, `reconciliation_refs`, `amount`, `currency`, `cost_category`, `authority_refs`, `source_event_ids`, and `warnings`.

### Utilization projection

Minimum fields: `utilization_item_id`, `resource_or_lane_ref`, `period_start`, `period_end`, `capacity_minutes`, `committed_minutes`, `available_minutes`, `overcommit_flag`, `source_task_ids`, and `warnings`.

### KPI projection

Minimum fields: `kpi_item_id`, `kpi_name`, `definition_ref`, `measurement_period`, `numerator`, `denominator`, `value`, `threshold`, `status`, `source_projection_refs`, `source_event_ids`, and `warnings`.

### Timeline projection

Timeline projections must separate active execution, validation, expected rework, integration time, queue wait, human/Steward review wait, blocked dependency wait, total machine-active time, and expected wall-clock elapsed time. Day-based values may only appear as secondary conversions when external waits justify them.
