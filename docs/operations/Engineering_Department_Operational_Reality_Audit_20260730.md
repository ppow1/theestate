# Engineering Department Operational Reality Audit

**Date opened:** 2026-07-30  
**Campaign:** Grace–Engineering Operational Activation  
**Branch:** `recovery/grace-engineering-operational-activation`  
**Status:** INVESTIGATING  
**Audit purpose:** Determine whether Engineering exists as a staffed, reasoning, callable department or whether current behavior consists primarily of governance records, deterministic state transitions, provider adapters, and demonstrations.

---

## 1. Preliminary Verdict

**Current verdict: PARTIALLY OPERATIONAL, BUT A STAFFED REASONING ENGINEERING DEPARTMENT IS NOT YET VERIFIED.**

The repository contains substantial Engineering execution infrastructure. It also contains an external Engineering Worker Runtime adapter and a reusable Dispatch bridge. However, the first inspected implementation does not yet demonstrate an LLM-backed Engineering resident or supervisor performing technical planning, provider comparison, provider selection, artifact review, retry judgment, or completion judgment.

The current observed path appears capable of moving a bounded package through Helen-, Grace-, Dispatch-, external-runtime-, validation-, and closure-labeled records. That is meaningful infrastructure, but it is not yet proof of the institutional Engineering reasoning layer described by the Steward.

## 2. Evidence Examined at Checkpoint 1

### 2.1 `src/estate/core/local_engineering_department.py`

Observed:

- The Estate-side module explicitly describes itself as an adapter for an external worker runtime at `A:\AI\Tools\EngineeringWorkerRuntime`.
- It validates a manifest and invokes the external entrypoint as a Python subprocess with a bounded package, worktree, and evidence directory.
- It creates Helen staffing records programmatically for a hard-coded role and hard-coded worker identity: `local-engineering-worker-001`.
- The Helen assessment rationale and qualification result are authored directly by deterministic Python in the same method that requests staffing.
- `run_closed_loop()` is hard-coded to CAMPAIGN_0550 and WP-0552.
- The closed loop creates a Grace objective, requests Dispatch, invokes the external worker, runs repository-wide production readiness validation, updates Dispatch, and closes the Grace objective.
- Grace closes the objective with `accepted=False`, preserving higher acceptance authority.
- The reusable seam is `run_dispatch_bridge(dispatch_id)`.

Initial classification:

| Capability | Classification | Reason |
|---|---|---|
| Estate governance/control-plane adapter | OPERATIONAL | Executable Python adapter exists. |
| External runtime invocation | PARTIALLY OPERATIONAL | Invocation contract exists, but the production runtime contents and live installation have not yet been verified. |
| Helen workforce records | SIMULATED / DETERMINISTIC | Staffing evidence is generated by the department method itself for a fixed worker; no independent worker discovery or qualification reasoning has yet been observed. |
| Grace objective and Dispatch record creation | OPERATIONAL, PARTIAL | Durable records and handoff exist; general institutional intake remains incomplete. |
| Engineering reasoning worker | UNVERIFIED | No LLM/model-backed planning or judgment was observed in this module. |
| Provider selection by Engineering | UNVERIFIED | The inspected closed loop does not show Engineering comparing or selecting providers. |
| Engineering validation judgment | UNVERIFIED | A deterministic production-readiness report is generated; no Engineering worker review/judgment has yet been observed. |

### 2.2 `tests/test_local_engineering_department.py`

Observed:

- Tests materialize the external runtime by copying repository fixtures from `external/engineering_worker_runtime` into a temporary mapped runtime path.
- Tests verify that records, hashes, paths, and state transitions are created.
- Tests verify hard-coded ownership by `local-engineering-worker-001`.
- A Dispatch bridge test supplies the provider `codex-cli-openai` directly in its test payload rather than demonstrating Engineering reasoning that selects that provider.
- The tests establish contract and plumbing behavior, but do not prove the installed production runtime is present, model-backed, reasoning-capable, or institutionally staffed.

Initial classification:

| Test claim | What it proves | What it does not prove |
|---|---|---|
| Closed loop completes in `tmp_path` | The fixture runtime and Estate adapter can create expected records and evidence. | That the live `A:\AI\Tools\EngineeringWorkerRuntime` exists and functions today. |
| Helen/Grace/Dispatch boundaries are recorded | Contract-shaped records are created. | That Helen independently evaluates a real worker or that Engineering makes technical decisions. |
| Dispatch bridge completes | A preconfigured Dispatch item can be passed to the fixture runtime. | That Engineering selects the provider or validates the returned work through reasoning. |

### 2.3 `docs/architecture/engineering_department_current_state_map.md`

Observed:

- The repository's own July 16 assessment classifies the local Engineering department adapter as `active, partial`.
- It says `run_closed_loop()` is fixed to CAMPAIGN_0550/WP-0552 and `run_dispatch_bridge()` is the reusable seam.
- It classifies Open WebUI Engineering workflow as experimental and explicitly says it performs no provider execution.
- It identifies provider routing as recommendation-only and Engineering provider views as partial.
- It states there is no single Engineering campaign intake/status/advance command.
- Its observed end-to-end path says staffing association is ad hoc, Grace assignment requires a caller, provider selection is not bound to a shared campaign/package record, operator authorization is required, and campaign acceptance lacks a canonical package/gate ledger.
- Its baseline conclusion says the major execution primitives exist but the shared Engineering campaign/work-package lifecycle contract is missing.

Initial interpretation:

The existing repository assessment supports the Steward's concern. Engineering has many primitives and a bounded execution bridge, but the department is not demonstrated as a continuously staffed reasoning institution capable of receiving an arbitrary commission and deciding how to fulfill it.

## 3. First Confirmed Findings

### F-001 — Engineering infrastructure exists

**Status:** VERIFIED

The repository contains real Python for governance records, Dispatch handoff, external runtime invocation, validation reports, evidence hashing, and closure records.

### F-002 — The first local Engineering loop is a bounded demonstration

**Status:** VERIFIED

The principal closed-loop method is hard-coded to CAMPAIGN_0550/WP-0552 and a fixed worker identity. The repository's own current-state map calls it active but partial.

### F-003 — Staffing is currently represented by deterministic record construction in the inspected path

**Status:** VERIFIED FOR THIS PATH

The same Python method creates the staffing request and then creates a favorable Helen assessment for `local-engineering-worker-001`. Independent runtime discovery, model identity, availability, or qualification evaluation has not yet been observed.

### F-004 — A reasoning Engineering worker has not yet been located

**Status:** UNVERIFIED / OPEN

No inspected code yet shows an LLM-backed worker receiving the commission, interpreting the specification, comparing providers, selecting an execution method, reviewing artifacts, or deciding whether to retry or approve.

### F-005 — Existing tests primarily prove plumbing and fixture behavior

**Status:** VERIFIED

The tests materialize a repository fixture into a temporary runtime and verify durable state and evidence. Live production installation and institutional reasoning remain to be verified separately.

### F-006 — Provider choice is not proven to belong to Engineering

**Status:** VERIFIED AS A GAP IN THE INSPECTED TEST

The Dispatch bridge test supplies `codex-cli-openai` in its input payload. That proves bounded execution of an already selected provider, not Engineering provider-selection judgment.
