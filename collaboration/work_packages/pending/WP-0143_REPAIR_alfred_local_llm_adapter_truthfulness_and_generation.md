# REPAIR TASK WP-0143 - Repair Alfred Local LLM Adapter Truthfulness and Generation

Read collaboration/work_packages/pending/WP-0143_REPAIR_alfred_local_llm_adapter_truthfulness_and_generation.md and do exactly what it says.

## Mode

REPAIR

## Problem

The Steward has confirmed that the Steward Command Center shell is now functioning well enough to test Alfred. The only visible browser console issue is a favicon 404, which is not the operational problem.

The operational problem is now Alfred's local LLM adapter truthfulness and generation behavior.

Observed behavior from the Steward browser:

- The Command Center is served at `http://127.0.0.1:8765/`.
- The Alfred panel opens.
- Alfred accepts input and returns a visible response.
- The console shows only a favicon 404, not the prior script failure.
- The Steward asked Alfred to tell a new joke multiple times.
- Alfred returned the same skeleton joke repeatedly:

```text
Here's a light-hearted joke for you: "Why don't skeletons fight each other? They don't have the guts!"
```

- The response metadata shown in the UI claims something equivalent to:

```text
Mode: local_llm
Type: direct_conversational_response
request: 2026-07-06T16:32:09+00:00
response: 2026-07-06T16:32:11+00:00
fallback: local Ollama models discovered via http://127.0.0.1:11434/api...
```

The Steward correctly identifies this as evidence that Alfred is not actually using a generative local LLM response path, or that the UI/metadata is misrepresenting deterministic fallback as local LLM output.

Repeatedly returning the same canned joke when asked for a new joke is acceptable only if the system clearly says deterministic fallback was used. It is not acceptable to label that response as `local_llm`.

## Primary Root-Cause Questions

Codex must answer these directly in the report:

1. Did Alfred actually call a local LLM generation endpoint for the joke response?
2. If yes, which endpoint, provider, and model were used?
3. If yes, what prompt was sent and what response came back, after safe redaction?
4. If no, why did the UI report `Mode: local_llm`?
5. Why does the response metadata mention fallback while also reporting local LLM mode?
6. Is Alfred discovering Ollama models but failing to generate from them?
7. Is Alfred selecting a model but never calling generation?
8. Is Alfred using deterministic fallback while labeling it as local LLM?
9. Is the repeated skeleton joke hard-coded in the fallback path?

## Required Repair Outcomes

### 1. Truthful Mode Reporting

Alfred response metadata must distinguish:

- `local_llm_generated` — a local model generation endpoint was actually called and returned the final response;
- `local_llm_discovered_but_generation_failed` — models/endpoints were found, but generation failed;
- `deterministic_fallback` — no generation endpoint produced the response;
- `transport_failed` — browser/API transport failed;
- `blocked_privileged_execution` — governed action request refused from chat.

Do not report `Mode: local_llm` unless the final visible response was actually generated by the local LLM.

### 2. Generation Must Be Invoked When Available

If a local LLM provider is available and a model is selected for Alfred, Alfred must attempt generation for ordinary conversational prompts before falling back.

For Ollama, inspect existing adapter behavior and ensure the correct generation endpoint is used. Depending on existing adapter conventions, this may be one of:

```text
POST http://127.0.0.1:11434/api/generate
POST http://127.0.0.1:11434/api/chat
```

Use existing adapter standards if already defined. Do not invent a second unrelated adapter.

### 3. Discovery Is Not Generation

Finding models through `/api/tags` is not the same as generating a response.

The UI must not present model discovery as proof that Alfred used the local LLM.

### 4. Fallback Must Be Honest

If deterministic fallback is used, the UI must show that clearly.

Example acceptable metadata:

```text
Mode: deterministic_fallback
Reason: local LLM generation unavailable: <safe reason>
Provider discovered: ollama
Selected model: <model or none>
```

### 5. Repeated Joke Behavior

If fallback must provide jokes, it should not always return the same skeleton joke.

At minimum:

- provide a small deterministic rotating set based on prompt/session/turn timestamp, or
- return a truthful statement that fallback has limited novelty.

If a local LLM generation path is available, joke novelty should come from the model, not a hard-coded memory joke.

### 6. Local LLM Diagnostics

Expose safe diagnostics per Alfred response:

- provider;
- endpoint;
- discovered models count;
- selected model;
- generation attempted true/false;
- generation endpoint used;
- generation result state;
- fallback active true/false;
- fallback reason;
- sanitized error if any;
- request timestamp;
- response timestamp.

Do not expose secrets or full sensitive prompts if artifacts include private text. A short safe prompt summary is enough.

### 7. Tests

Add or update tests proving:

1. If the local LLM adapter returns generated text, Alfred response mode is `local_llm_generated` and the generated text is shown.
2. If models are discovered but generation fails, Alfred response mode is not `local_llm_generated`.
3. If deterministic fallback is used, UI metadata says deterministic fallback.
4. A joke prompt does not always return the same hard-coded skeleton joke across repeated turns when fallback is used.
5. Discovery of Ollama models through `/api/tags` alone does not mark the final response as generated by local LLM.
6. Safe diagnostics include generation attempted/result state.
7. No adapter diagnostics leak secrets.
8. Existing Alfred governed-action boundary remains intact.
9. Existing resident interaction persistence remains intact.
10. Existing Command Center navigation/shell tests remain passing.
