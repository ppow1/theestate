# SERIES TASK WP-0127 — Alfred Operations Center Chat Implementation

## Codex Command

Read collaboration/work_packages/pending/WP-0127_SERIES_alfred_operations_center_chat_implementation.md and do exactly what it says.

## Mode

SERIES

## Mission

Implement Alfred as the first resident using the WP-0126 resident interaction framework.

The Steward must be able to open the local Office of the Steward / Operations Center UI, see Alfred as the front-door resident assistant, type to Alfred, receive a useful response, and have the interaction persisted through the resident interaction framework.

This package must not rebuild the generic framework. It must consume and validate the WP-0126 framework.

## Background

WP-0126 establishes the reusable resident interaction framework, local LLM governance, persisted resident conversation memory, Steward-controlled forgetting/redaction, versioned resident API standards, versioned resident implementations, and controlled resident API/surface extension.

WP-0127 applies that framework to Alfred.

Alfred is the Steward's first point of contact with the Estate. He must no longer feel like a command-initiated report generator. He must be present in the Office while the local Operations Center is running.

## Scope

In scope:

1. Add Alfred chat UI to the Office of the Steward / Operations Center.
2. Make Alfred visible on the Home/front-door surface and Alfred tab.
3. Wire Alfred chat UI to the resident interaction framework from WP-0126.
4. Use Alfred's resident API/surface profile and implementation version.
5. Use local LLM mode where available through the WP-0126 adapter path.
6. Use deterministic fallback only when local LLM is unavailable in the execution environment.
7. Display prior Alfred conversation history or provide a reloadable history view.
8. Provide a visible send/submit interaction.
9. Provide visible authority/memory messaging so the Steward understands what Alfred can and cannot do.
10. Ensure Alfred chat does not execute privileged actions without authority.
11. Persist Alfred chat turns using the framework.
12. Expose or link Alfred's inspectable resident API/surface from the Alfred UI or report.
13. Add validation recipe and completion receipt for WP-0127.

Out of scope:

- Rebuilding the resident interaction framework from WP-0126.
- Implementing full Helen/Ingrid/Chief Architect #5 chat surfaces.
- Creating the Character Development Engineer role.
- Implementing mood arcs or character-development behavior.
- External Codex telemetry.
- Full command palette implementation.
- Cloud LLM/API integration.
- Granting Alfred new authority beyond artifact-backed responsibilities.

## Required User Experience

When the Steward opens the local Operations Center:

1. Alfred is visible as the front-door resident assistant.
2. The Steward can type a message to Alfred.
3. The Steward can submit the message without using a terminal.
4. Alfred returns a visible response.
5. The response is generated through the resident interaction framework.
6. The conversation turn is persisted.
7. The UI can show or reload prior Alfred conversation turns.
8. The UI indicates Alfred's authority boundary and memory behavior.
9. The UI indicates local-first operation.

Minimum acceptable first interaction:

```text
Steward: Alfred, what should I look at first?
Alfred: Good morning, Pat. Current Estate status: [...]. Recommended next action: [...].
```

The answer must be generated by the actual Alfred/resident interaction path, not static placeholder HTML.

## Required Alfred Behavior

At minimum, Alfred must be able to respond to prompts by using available Estate context such as:

- current production-readiness status;
- resident status;
- pending work packages;
- Engineering Department / CueMastery status;
- Operations Center status;
- recent activity if available;
- known next actions.

If Alfred cannot answer a prompt yet, he must say what he can currently do and recommend a concrete next step.

Do not fake unavailable authority or unavailable model capabilities.
