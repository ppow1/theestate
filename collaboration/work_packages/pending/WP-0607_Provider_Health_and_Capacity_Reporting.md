# WP-0607 - Provider Health and Capacity Reporting

Status: Pending  
Author: Chief Architect #6  
Intended Executor: Codex  
Classification: Estate Internal

## Mission

Implement the first provider health and capacity reporting layer for the Estate.

The Estate is now moving from single-worker execution toward many concurrent workers and multiple provider classes. The Steward needs to know which providers are available, degraded, saturated, out of quota, blocked, or unknown before work is scheduled or assigned.

This package creates local health/capacity models, runtime status artifacts, CLI inspection commands, provider catalog integration, operational event compatibility, and tests.

This package does not execute providers and does not implement a scheduler.

## Architectural Intent

Provider selection and scheduling require operational awareness.

The Estate should not assign work to a provider without some visible understanding of provider status. That status may be approximate, manually recorded, or automatically probed, but it must be represented as structured state rather than hidden terminal knowledge.

This package supports:

`governed dispatch -> visible activity -> structured events -> auditable result -> Steward-visible decision state`

Do not create a new office. This is infrastructure for future Orchestrator and Office visibility.

## Provider Health Model

Implement and validate a provider health record with these fields:

- `health_id` string, required
- `provider_id` string, required
- `checked_at` ISO timestamp, required
- `reported_by` string, required
- `status` string, required
- `message` string, required
- `classification` string, required
- `source` string, default `manual`
- `expires_at` ISO timestamp, optional
- `capabilities_available` list, default empty
- `capabilities_unavailable` list, default empty
- `requires_attention` boolean, default false
- `metadata` object, default empty

Allowed health statuses:

- `available`
- `degraded`
- `saturated`
- `out_of_quota`
- `blocked`
- `offline`
- `unknown`

Allowed classifications:

- `Public`
- `Estate Internal`
- `Restricted`
- `Steward Only`
- `Local Only`

## Provider Capacity Model

Implement and validate a provider capacity record with these fields:

- `capacity_id` string, required
- `provider_id` string, required
- `checked_at` ISO timestamp, required
- `reported_by` string, required
- `capacity_state` string, required
- `active_jobs` integer, default 0
- `max_jobs` integer, optional
- `queue_depth` integer, default 0
- `quota_remaining` number or string, optional
- `quota_resets_at` ISO timestamp, optional
- `estimated_available_at` ISO timestamp, optional
- `classification` string, required
- `message` string, optional
- `metadata` object, default empty

Allowed capacity states:

- `idle`
- `available`
- `busy`
- `saturated`
- `quota_limited`
- `unknown`

Capacity values must never require live network calls.

## Summary Model

Generate a provider health summary with:

- `generated_at`
- `provider_count`
- `available_count`
- `degraded_count`
- `saturated_count`
- `blocked_count`
- `out_of_quota_count`
- `unknown_count`
- `providers` list of safe provider summaries

Each provider summary should include:

- `provider_id`
- `display_name` when available from catalog
- `provider_type` when available from catalog
- `health_status`
- `capacity_state`
- `active_jobs`
- `max_jobs`
- `queue_depth`
- `requires_attention`
- `last_checked_at`
- `safe_message`

Sensitive messages must be redacted unless metadata marks `summary_safe: true`.

## CLI Requirements

Add commands using existing Estate CLI conventions.

Preferred commands:

```powershell
Clear-Host
cd A:\theestate
.\estate.bat providers-health-set --provider-id codex.execution.cli --status available --reported-by Steward --message "C2 available"
.\estate.bat providers-capacity-set --provider-id codex.execution.cli --capacity-state busy --active-jobs 1 --reported-by Steward
.\estate.bat providers-health-summary
```

Commands must:

- validate provider ID against catalog when catalog is available,
- allow manual status recording when catalog is unavailable but warn clearly,
- write runtime records,
- update latest and summary artifacts,
- print concise output,
- exit non-zero for malformed input.

If existing CLI routing uses another pattern, follow it and document actual commands.

## Boundary Behavior

- Provider health summaries must not contain secrets, tokens, raw account identifiers, private prompts, or personal data.
- Restricted, Steward Only, and Local Only messages should be redacted unless `summary_safe: true` is present.
- Structural fields such as provider ID, state, and capacity may be shown unless explicitly classified otherwise.
